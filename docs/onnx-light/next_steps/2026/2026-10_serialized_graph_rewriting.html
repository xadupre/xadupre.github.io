Serialized graph rewrites and model variants#

Date:

2026-10-20

Steps 1 through 4 implemented: proto records, replay, model envelope and Python export. The optimizer captures initializer recipes and shared function definitions in LocalRewritingProto / RewritingProto. GraphBuilder::ApplyRewritings (Python: builder.apply_rewritings) returns a new builder, prepares constants once and preserves model-level additions. GraphBuilder.to_onnx exports the canonical model by default (OptimizationMode.kNone), the optimized result with optimize=OptimizationMode.kOptimize, or the canonical model with its captured plan with optimize=OptimizationMode.kRewritings.

Existing building blocks#

PatternOptimization implements recognition (Match) and replacement construction (Apply), in C++ or Python. MatchResult identifies one match. GraphGraph::Optimize returns a RewritingProto containing ordered LocalRewritingProto edits: matched node positions, added nodes and their positions, added/removed initializers and subgraph path. Reversible capture starts from the cleaned canonical graph, after all cleanups that redirect value references.

builder.ApplyRewritings(rewrites) reconstructs a GraphBuilder without running the matcher. Matched and removed positions refer to the graph immediately before each edit; added positions describe its result. Internal optimizer batches are normalized to this sequential coordinate system. Later edits may consume nodes created by earlier ones. Normalization keeps an indexed live order and materializes the final sequence once. Retained nodes displaced across other retained nodes are explicitly recorded in the edit, so replay preserves subsequent positional coordinates. These records own snapshots of displaced nodes, independent of later cleanup and mutations of the live builder. Every rewrite immediately maintains dependency-consistent node order, shapes, and compute annotations. Coordinates refer to that actual order, so the returned builder can receive another plan, including an empty plan, without exporting first. New producers are inserted before existing consumers whenever their own inputs permit it. Otherwise, only blocked consumers and their affected consumers are displaced. Independent retained nodes keep their relative order. Mutations do not topologically sort the graph, and export only uses that fallback if a dependency-order violation is actually detected.

The two rewrite messages support binary serialization and Python bindings. Records contain a diagnostic pattern name, not a live pattern pointer or timings. Timing remains in OptimizationReport. ModelProto.rewritings stores independently named plans against the canonical graph.

Constant folding retains the computation as shared functions and ordered initializer_calls, not materialized results in added_initializers. Literal constants still use added_initializers. Removed definitions and payloads needed to undo reversible edits are retained only in the optimizing GraphBuilder, separately from the serialized removal positions. Neither rewriting proto nor exported models contain undo history. The forward recipe avoids embedding a transposed payload in added_initializers.

TransposeToInitializerPattern is no longer needed: it only re-emitted an unchanged Transpose to trigger folding. The optimizer captures preparation nodes produced by actual rewrites (for example, TransposeTransposePattern) as shared FunctionProto recipes. An untouched constant Transpose remains in the canonical graph; explicit GraphBuilder::ConstantFold still folds it when materialization is desired.

The messages are defined in onnx_proto/include/onnx_proto/onnx.h using the existing protobuf-free message layer. The schema below includes fields used by constant preparation. The returned builder exposes BuildGraph() for a graph-only result and ToModel() to export the graph together with its functions and opset imports.

Decision: use protos as runtime records#

Use ``LocalRewritingProto`` as the record used by the optimizer and existing replay engine. RewritingProto holds the ordered records and their shared function definitions/imports. Do not maintain parallel C++/proto records or introduce a second replay engine and conversion layer. Undo-only information is private, non-serialized builder state; it does not extend these forward proto records.

Migrate Optimize results, replay arguments, cleanup recording, C++/Python bindings, diagnostics, tests and examples to the new messages. Keep matching and MatchResult separate: the live pattern pointer belongs to matching, not the recorded edit. Applying rewrites must not require that pointer while retaining its structural validation. Keep timing in OptimizationReport rather than requiring it in replay records.

Optimize + capture recipes -> RewritingProto -> GraphBuilder::ApplyRewritings
                                    |
                           file / ModelProto.rewritings

The proto sequence applies one rewrite at a time: matched/removed positions refer to the graph immediately before that rewrite, and added positions to its result. There is no serialized iteration or batch ID. If the optimizer still applies internal batches, normalize their positions when producing the ordered proto records: rebase node/initializer positions and affected subgraph paths after each preceding edit. Internal batching may remain an implementation detail, not a second persistent record format. Verify that sequential replay preserves the batch result. Check integer ranges before converting proto positions to size_t. Normalization indexes insertion anchors and maintains live node and initializer ranks incrementally; it does not rescan or sort the full live order per edit.

New and modified proto messages#

The wire schema is below. The first two messages use onnx-light’s existing BEGIN_PROTO / FIELD_* layer, parser and serializer, without adding a protobuf compiler or libprotobuf. Step 3 added the ModelProto.rewritings field.

// New messages; NodeProto/TensorProto and the other ONNX messages exist.
message LocalRewritingProto {
  string pattern_name = 1;
  repeated string graph_path = 2;
  repeated uint64 matched_nodes = 3;
  repeated uint64 removed_initializers = 4;
  repeated NodeProto added_nodes = 5;
  repeated uint64 added_nodes_positions = 6;
  repeated TensorProto added_initializers = 7;
  repeated uint64 added_initializer_positions = 8;
  reserved 9;
  reserved "value_renames";
  repeated StringStringEntryProto metadata_props = 10;
  repeated NodeProto initializer_calls = 11;
  repeated uint64 computed_initializer_positions = 12;
  repeated uint64 removed_extended_initializers = 13;
}

message RewritingProto {
  repeated LocalRewritingProto rewrites = 1;
  repeated OperatorSetIdProto required_opset_imports = 2;
  repeated StringStringEntryProto metadata_props = 3;
  repeated FunctionProto added_functions = 4;
}

Removal positions are relative to the corresponding initializer list before each edit: removed_initializers indexes dense initializers, removed_extended_initializers indexes the unified GraphProto.extended_initializer list of encoded constants and paged caches. Both payload alternatives share this index space and retain their declaration order across builder import/export and replay.

The optimizing builder retains removed definitions in the same order as their removal positions. Its in-memory undo history also preserves graph declarations, counts and expected replacements needed for strict restoration. This history is not part of either proto: a serialized plan contains only forward edits, and a removal position alone cannot restore a definition.

Modify only onnx-light’s ``ModelProto`` to add map<string, RewritingProto> rewritings, keyed by variant name, without introducing another named proto message in this plan. Reserve and document its extension field number before implementation: field 1001 is reserved for this map, following struct_types at 1000 within ModelProto’s local 1000-1099 extension range. Reject duplicate keys. Each map entry uses the protobuf map encoding (string key at field 1, RewritingProto value at field 2); no additional public proto message is introduced.

NodeProto, GraphProto, TensorProto, FunctionProto and OperatorSetIdProto need no new fields. Their existing forms carry the replacement graph data. Extend model binary I/O and Python bindings to expose and preserve the new field. This is an onnx-light extension, not a standard ONNX field or an upstream ONNX schema change.

The local proto replaces the live pointer with its diagnostic pattern name. Producer identity uses the existing ModelProto.producer_name and producer_version fields. Do not serialize timings in V1: they are not required for replay. Both LocalRewritingProto.metadata_props and RewritingProto.metadata_props carry optional descriptive key/value metadata, not executable compatibility rules. Runtime schema and kernel checks must not depend on these annotations. Imports are collection-level additions checked against the canonical model, not permission to reinterpret surviving operators.

Deferred constant folding and added functions#

Optimizer capture populates LocalRewritingProto.initializer_calls and computed_initializer_positions directly. Collect and deduplicate definitions across all local edits into RewritingProto.added_functions during capture. Local records contain calls, not repeated definitions. Capture the folded operations and their dependencies before ConstantFoldNodes discards them, and package the computation as a FunctionProto with explicit inputs and outputs. Calls use NodeProto:

RewritingProto.added_functions:
  PrepareWeights(W) -> WT { WT = Transpose(W) }
LocalRewritingProto.initializer_calls:
  WT = PrepareWeights(W)
LocalRewritingProto.computed_initializer_positions:
  [position of WT in the resulting initializers]

Call inputs reference existing initializers or preceding call outputs. Calls are ordered, evaluated once during variant preparation, and their outputs become initializers, not per-inference graph nodes. Flatten call outputs in call/output order to associate them with computed_initializer_positions. These positions and added_initializer_positions share the resulting initializer coordinate system and must not overlap.

Read source constants and compute call results before deleting any referenced initializers. Then apply removals and install literal/computed initializers and replacement nodes. Keep added_initializers for literal constants; do not serialize a computed payload as well as its recipe. Rebasing to sequential records must preserve preparation dependencies and positions too.

Before applying local edits, ApplyRewritings merges collection-level functions: add absent definitions, reuse identical definitions, and reject conflicting definitions with the same identity, including conflicts between local edits during capture. Return a new GraphBuilder containing the merged functions/imports, and use its existing BuildGraph / ToModel exports rather than separate graph/model replay functions. Update dependent callers explicitly. Validate constant-only, deterministic preparation operations and available implementations; do not execute arbitrary stateful functions as initializer recipes.

This avoids storing a second transposed weight payload in the file, not necessarily allocating a second buffer during preparation. Reuse a view only when supported by the tensor representation and consumer. Materialized plain ONNX export may intentionally store computed weights instead.

LocalRewritingProto has no value-renaming field. Field number 9 and the former name value_renames are reserved and must not be reused. Binary plans containing that field and text plans using that name are explicitly rejected; regenerate these plans instead of silently dropping their renaming effects. Removing b = Identity(a) redirects consumers of b to a but does not identify which consumers already used a. Inverting that substitution is deliberately outside the reversible-plan contract.

Identity removal, duplicate-node elimination and initializer deduplication therefore run before capture, including in nested graphs. They establish the canonical graph and are not themselves recorded as reversible edits. Do not repeat these renaming cleanups between recorded rewrites; replacements may use fresh internal names but must preserve names at their boundaries.

Inverse replay processes recorded edits in reverse application order. It restores only definitions removed by these edits, never Identity nodes or duplicate constants removed before capture. It validates positions, expected replacement definitions and subgraph paths, and explicitly rejects builders lacking the in-memory information needed for exact restoration. A failure must not leave the caller’s builder partially restored.

GraphGraph::Optimize automatically canonicalizes before capture; no Python canonicalization method is needed. Export obtains the cleaned reference from the optimizing builder’s in-memory undo history. Ancestor substitutions are applied before cleaning descendant scopes, so canonicalization is idempotent even when captured values become equivalent. Annotations for values removed by these cleanups are pruned before capturing the reference, including when no reversible edits follow. Shape/Size nodes are moved next to their producers before capturing edit positions, so subsequent canonical-model export does not invalidate those positions. This reordering preserves incremental tags and updates affected lifetime and memory metadata without rebuilding graph analysis. Identity nodes and duplicate constants introduced by recorded replacements remain in place: cleaning them up would redirect references after capture and is outside the reversible-plan contract. Consequently, later patterns may not match across newly introduced Identity boundaries. GraphBuilder::UndoRewritings (Python: builder.undo_rewritings(plan)) returns a new builder at the cleaned canonical state. It requires the builder that performed optimization and its matching plan. Exporting and reloading an optimized model does not retain this history; applying a serialized forward plan to a fresh builder does not recreate it either. Structural and declaration mutations invalidate both named plans and the private undo capture, including when a nested builder invalidates its ancestors. A stale plan is rejected without changing the mutated builder. Moving an unchanged optimizing builder preserves its capture.

Unit tests verify complete canonical/optimized graph roundtrips. Production capture and undo do not retain an optimized-graph validation snapshot, compare whole graphs, or execute forward replay merely to check their own correctness. The supplied plan is compared directly with the captured plan, without serialization, and local edit bounds and payload checks remain. Independent node edits share indexed live-order tracking during both inverse capture and undo; their node lists are materialized once per batch, and unchanged initializer lists are retained. Undo uses the optimized graph directly rather than requiring its incrementally preserved tags to match fresh shape inference. Forward replay retains its strict tag validation. Device targets for the canonical root, subgraphs and local functions are captured privately and restored by undo, including scopes removed during optimization. Canonical value/node tags and custom node-tag override flags are also restored exactly, including after repeated optimization captures; affected shape-tagged release lists and memory profiles are refreshed. Function definitions are collected from every scope, including functions owned by branches that are hoisted into the restored model. None of this metadata or inverse history is serialized. The initial Python model is released as soon as the working builder has imported it, before optimization and inverse capture. Existing named plans are retained in private undo history when cleanup reports that the canonical reference is unchanged. Cleanup changes in nested graphs and functions invalidate those plans without another whole-model export or equality scan.

Builder import/export and private undo definitions use explicit tensor-storage snapshots: message structure remains independent, while unchanged owned raw buffers and typed tensor arrays share storage until a mutable container access detaches it. Nested graph attributes, local functions, recipes and removed initializer definitions use the same mechanism. Ordinary proto copies retain their existing semantics; sharing is requested with utils::CopyWithSharedTensorStorage rather than enabled globally. Here, tensor storage means the allocation containing raw bytes or typed tensor elements, not the tensor’s name, dimensions, element type or other metadata. The named copy operation explicitly walks each message field and propagates to nested containers and messages. It uses no mutable global or thread_local copy mode; ordinary constructors and CopyFrom never depend on an ambient copy context. Comparison and copying share the same native field catalogue. Shared copies also preserve private oneof discriminators, including in nested messages, so entering an already-active alternative does not clear its value. Borrowed buffers with an owner retain that owner and remain read-only through the proto API. Ownerless borrowed buffers are copied into safe owned storage. As with the existing zero-copy import APIs, callers must not modify borrowed storage externally while it is in use. Mutable C++ pointers, iterators and references obtained before a snapshot boundary must be reacquired afterward. Active exported raw-data views use a copy fallback. Genuinely transformed weights receive new allocations; undo retains the original definitions needed for exact restoration, not additional copies of their unchanged bytes. Node deduplication hashes native attribute contents without serializing large Constant tensors into strings. Hash hits are checked with native equality, including resolved inputs and attribute multiplicity; local-function weights use the same bounded-memory path. Local-function shape inference also explicitly shares tensor payloads when copying body nodes and binding call-site attributes.

Integer, FLOAT and DOUBLE value bounds are scanned directly from typed fields or little-endian raw payloads without a decoded tensor-sized temporary. Payload counts must still match the tensor dimensions before bounds are recorded. Python indexing, iteration, representation and list comparison of numeric fields use const storage access and leave shared payload allocations intact. Neutral arithmetic vectors are checked directly against their payloads as well, including all-zero weights and weights whose first value alone is neutral. Typed fields take precedence over raw bytes, and vector rewrites still require an exact payload count and matching last-dimension broadcasting. Owned storage with active NumPy/DLPack views rejects mutable access, byte assignment, resizing and appending with an exception. Release all consumers before modifying that storage; clearing the tensor retains the old allocation for existing views. Failed owned-buffer resizing preserves the original bytes, logical size and alignment, including when detaching a shared allocation within its capacity. Successful aligned resizing copies the logical prefix to the new aligned address, not the old backing allocation’s padding; conversion to plain storage preserves that prefix as well. Tensor and encoded-value raw-data setters retain aliased source storage until copying finishes, including aligned self-assignment and self-slices. Appending to a full shared buffer allocates only the grown buffer, without first allocating a same-sized detached copy.

Initial graph
  -> renaming cleanups
  -> cleaned canonical graph
  -> capture and apply reversible rewrites
  -> optimized graph
  -> inverse replay
  -> cleaned canonical graph

Every variant starts from the canonical model containing it, not another variant. Standalone distribution of rewrite plans is outside this proposal. Any modification to the source model must clear or regenerate its variants. Without a source fingerprint, structural validation alone cannot detect every stale plan; maintaining this association is the responsibility of model mutation and export APIs.

This serializes matched edits, not a general declarative matching language.

Export workflow#

The model-envelope API reserves field 1001 for ModelProto.rewritings. ModelProto.add_rewriting (C++ add_rewritings) and GraphBuilder.add_rewriting (C++ AddRewriting) reject duplicate names. GraphBuilder.apply_rewritings(name) (C++ ApplyRewritings) selects exactly one independent plan using existing replay and checks reachable operator implementations, including local functions and nested graphs. The replay result has no attached variants. Loading a model never executes its plans. The method is overloaded to accept either a RewritingProto or a plan name. GraphBuilder mutations invalidate the map, including mutations in nested builders and finalization that changes node order. Finalize before attaching plans. Callers editing proto fields directly must explicitly clear or regenerate the map; no source fingerprint or hidden repair is performed. ORT and standard-model export reject attached variants rather than dropping them. Python to_onnx(optimize=OptimizationMode.kOptimize) optimizes an independent builder and exports the materialized result without attached variants; model export rejects nonstandard fields through to_standard_model. to_onnx(optimize=OptimizationMode.kRewritings) instead returns the finalized canonical model with the captured plan named "optimized". It rejects a duplicate name and requires model export. Other plans can only be retained when their canonical reference remains unchanged; renaming cleanups invalidate plans against the earlier graph. The default OptimizationMode.kNone continues to export the current builder without running optimization. Only members of OptimizationMode are accepted. Both modes use the existing global and builder-local pattern registrations. The source remains at its finalized state; the independent working copy is automatically cleaned before capture. Bundled export recovers its canonical reference using the working builder’s in-memory undo history. Load external weights before optimization and use the existing external-data save options to relocate the payloads with either export. See Replaying graph-rewriting patterns.

  1. Finalize the canonical model first, including cleanup, ordering, names, imports and external-data layout.

  2. Optimize an independent copy for each selected target, recording only reversible edits after the renaming cleanups. Capture constant computations as functions/calls instead of embedding computed weight payloads. The optimizer returns RewritingProto directly; optionally attach descriptive metadata. Verify replay against direct optimization before publishing the variant. Inverse replay reconstructs the cleaned reference without retaining the original Python canonical model or undoing pre-capture cleanups.

  3. Export either the untouched canonical model, a bundled onnx-light model containing the canonical graph and rewrite map, or a standard ONNX model with one selected variant materialized and the extension map removed.

Bundling is opt-in. Do not replace the canonical graph while retaining positions that refer to its previous contents. Renaming, reordering or transforming the source invalidates its variants; regenerate them rather than silently reusing stale positions. When saving elsewhere, relocate or copy external payloads referenced by both canonical and replacement tensors. Do not assume other ONNX tools preserve unknown extension fields.

At load time, explicit variant selection validates positions, graph structure, schemas, kernels and resource requirements before replay on a working model. A requested incompatible variant fails with a clear error; canonical execution remains an explicit alternative, not a silent fallback.

Comparison with ORT runtime fusion#

ORT issue #33403 proposes optional runtime fusion packages that match the graph after EP assignment and submit replacements using existing kernels. This proposal instead records concrete edits during export and bundles them with the canonical model for later apply_rewritings, without rerunning the matcher. Updating export-time matching decisions requires regenerating the affected plans; ORT’s proposed packages can update matching and adapter logic independently of the canonical artifact. Runtime matching can account for actual EP ownership and session kernel availability, whereas serialized variants must be selected and validated against the target runtime. Both approaches keep a canonical graph, but differ in when rewrites are discovered and how they are distributed.

Rewrite definitions can live outside the canonical graph: a Python exporter can construct and serialize RewritingProto records as data without providing a separately compiled runtime extension. Requiring exporters to ship a native fusion package would complicate Python-based export workflows; keep that requirement out of this design. ORT’s proposed runtime packages instead carry executable matching and adapter logic behind an experimental extension interface. Serialized edits still require compatible operator implementations in the target runtime, but the exporter need not supply a binary merely to describe those edits. The bundled model remains the proposed distribution format; this does not introduce standalone rewrite files.
