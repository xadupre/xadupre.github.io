Attention Kernel Design#

The registered Attention kernel separates node configuration, concrete shape planning, and compute. It supports ONNX Attention opsets 23 and 24 for FLOAT, FLOAT16, and BFLOAT16.

Descriptor and invocation plan#

AttentionDescriptor records attributes and optional input/output wiring, then validates opset rules, head counts, qk_matmul_output_mode, cache pairs, and nonpad_kv_seqlen availability. The registered adapter currently rebuilds this descriptor from the node on every invocation. Because the adapter does not receive the model’s opset directly, it infers opset 24 when a seventh input is present and opset 23 otherwise.

AttentionPlan is lightweight and rebuilt for each invocation because sequence lengths and strides may change:

Layouts and semantics#

Rank-four tensors use [B, H, L, D]. Rank-three tensors use [B, L, H * D] and require explicit Q and KV head counts. MHA, GQA, and MQA share one plan; group_size = q_num_heads / kv_num_heads maps Q heads to K/V heads without physically repeating K or V.

The plan supports boolean and FLOAT additive broadcast masks, bottom-right causal masking, softcap, tensor past_key/past_value, opset-24 nonpad_kv_seqlen, optional present outputs, and all four qk_matmul_output_mode values. A V head dimension may differ from the Q/K head dimension.

The registered adapter publishes Y and the requested optional outputs. present_key and present_value concatenate past and current state in the original storage type and always use rank-four layout.

Streaming

Short queries, tensor-cache inputs, and BFLOAT16, when materialized dispatch is not required.

Visits KV blocks with online softmax and retains one score tile plus row accumulators instead of an Lq x Lkv matrix.

Single key

Exactly one effective key, when materialized dispatch is not required.

Copies the value directly, or writes zero for a masked row.

The streaming recurrence maintains a running maximum, denominator, and unnormalized output for each query row. Causal and padding frontiers skip entire unavailable blocks; an all-false boolean-mask block is skipped as well. Arbitrary additive masks remain fully evaluated.

Conversion and packing#

Tiled FP16 execution keeps Q/K in their original storage type. It converts V into a worker-local KV tile immediately before the value product, retains FP32 accumulation, and narrows the final query tile directly into Y. Rank-three Q/K/V rows are packed only when their sequence stride requires it; packing and output scatter are tile-local for both FP16 and FP32. There is no immutable-input cache: every invocation reads the current source tensors.

FP16 streaming converts the current query row and the visited K/V blocks, including blocks spanning past and current state, rather than converting complete tensors. For short contexts, up to four score blocks are converted once per worker/head and reused across query rows within that invocation. Longer contexts retain one conversion block. BF16 streaming retains its FP32-accumulating codec path. Half-storage materialized execution deliberately retains its full conversion buffers for observable QK output and FP64 softmax.

The benchmark’s memory model bounds active attention scratch per worker. It does not include vector allocator capacity retained from earlier calls or internal GEMM packing panels, and should not be interpreted as measured RSS.

Scheduling, precision, and invariants#

Outer batch/head/query-row ranges are submitted through the session executor. Prefill exposes many independent rows, while short-query and decode shapes avoid forced parallel overhead. FP16 and BF16 streaming paths accumulate in FP32 and narrow only the final output. Explicit FP64 softmax uses the materialized path rather than weakening its precision contract.

Q, K, and V types must match, and cache tensors must match those types. Rank-three head counts must be positive, with the Q count divisible by the KV count. nonpad_kv_seqlen must be INT64. Invalid optional-input pairings and unsupported combinations fail explicitly. A fully masked query row produces zeros rather than NaN.

Execution telemetry#

Enable set_kernel_usage_recording(session, True) and inspect used_kernel_paths(session) to distinguish Attention.tiled, Attention.streaming, Attention.materialized, and Attention.single_key. Additional Attention.conversion.*, Attention.packing.*, and Attention.output.* records describe the selected storage decisions. The ordinary used_kernel_names(session) inventory still reports only onnx_light_cpu::Attention. Attention.output.tile describes the final row/tile write granularity, not the presence of an extra Y buffer: contiguous FP32 single-block products can write directly into Y. The conversion and packing records describe explicit attention scratch, not internal GEMM panels. BF16 streaming reports Attention.conversion.element for its scalar codec and FP32 query-row cache rather than claiming conversion-free execution.

tools/benchmark_attention_parity.py retains these records alongside raw alternating CPU/ONNX Runtime samples. Recording is disabled during timing. ORT worker spinning is disabled so its idle workers do not compete with the CPU implementation between alternating samples. The corpus includes aligned q128/kv128 cases, q129/kv257 tile tails, head dimensions 63/64/128/256, and short-query streaming cases for FP16 and FP32.

Native half-precision arithmetic#

QK products reuse the existing half-storage GEMM dispatch; softmax and value accumulation stay in FP32. AVX2/F16C accelerates conversion but does not provide native FP16 arithmetic. The validation host for this change has no AVX-512 FP16/BF16 support, so no throughput claim is made for those instructions. FP16 accumulation is not substituted for FP32 accumulation, and probabilities are not rounded to BF16 simply to use a native BF16 value product.

Issue 982: AVX2 tile products and short queries#

The 2026-10-24 investigation reproduced all 37 named gaps on an AMD EPYC 7763 virtual machine (four visible logical CPUs). Baseline code was f9adcb9; optimized code was b33e854. Both used onnx-light-cpu 0.2.0, GCC 13.3.0, CMake Release, and ONNX_LIGHT_CPU_MAX_SIMD_LEVEL=AVX2. The runtime dependencies were the onnx-light 0.2.0 CPython 3.13 Linux release wheel (tag commit 6400f0f812b13bc32469e405bd2f762ba3cba7f0), ONNX Runtime 1.31.0, NumPy 2.4.3, and ml-dtypes 0.5.4; Python was 3.13.16. The CPU extension linked the exact wheel libraries using matching tag headers and ONNX_LIGHT_CPU_PYTHON_STABLE_ABI=OFF.

Measurements used the registered backend cases without changing their models, inputs, or tolerances. Both backends used one thread and affinity CPU 0, with 20 warmups and up to 100 alternating samples (one second per candidate). ORT used sequential execution, one inter-op thread, and disabled intra/inter-op spinning. With one effective thread neither backend has idle worker threads competing between samples. Compilation and profiling did not overlap timed runs. The runner checked every output against ORT before timing.

Two bottlenecks were isolated by dispatch A/B measurements:

  • The tiled probability/value product repacked already contiguous attention tiles through general GEMM. Calling the existing six-row AVX2/FMA microkernel directly avoids that packing and inner scheduling. The fast path is bounded to V dimensions 16–256 and at most 512 keys. Full 128-row tiles with V dimensions above 64 retain general GEMM, since measurements did not establish a benefit there. Outer runtime scheduling is unchanged.

  • Short queries reread K/V row by row. Eligible FP32/FP16 queries with 8–15 rows now reuse tiled products; aligned FP16 queries with 16 rows no longer take the old streaming override on AVX2/FMA. An invocation-local vectorized finite-value check preserves the old streaming behavior for NaN/Inf in V: streaming skips zero probabilities, whereas dense GEMM evaluates zero times NaN/Inf. This scan is inside the measured invocation; it is not cached. It shares the tiled product’s causal, window and per-batch nonpad bounds, so unavailable V prefixes and suffixes are not scanned. Rank-three scans include the interleaved KV heads only within the selected rows.

Both decisions cache CPU feature detection and leave unsupported CPUs, dimensions, tensor-cache inputs, sink attention, and materialized dispatch on the existing paths. Products retain FP32 accumulation and the existing softmax. No new packing buffer or executor is introduced.

Contiguous additive masks retain AVX2 decode for finite rows. Only rows with reachable NaN mask entries fall back to scalar streaming. Tiled AVX2 softmax also preserves NaNs computed by QK: a check limited to its otherwise-zero branch distinguishes these from fully masked rows. Normal finite blocks do not incur an extra score scan.

A gprof run of the new differential test, repeated 100 times, confirmed the six-row AVX2/FMA GEMM microkernel and AVX2 softmax execute. This includes materialized-oracle, data-generation, and assertion costs, so its self-time percentages are not end-to-end phase percentages. Hardware and software perf events were blocked by perf_event_paranoid=4.

Issue 986: short causal GroupQueryAttention on AVX2#

The 2026-10-25 reproduction used an AMD EPYC 7763 VM with four visible logical CPUs, GCC 13.3.0 Release, Python 3.13.16, and an AVX2 ceiling (reported SIMD level 3). Baseline production code was c945d91; the optimized code is b50c0fb. Dependencies were onnx-light-cpu 0.2.0, the onnx-light 0.2.0 CPython 3.13 Linux release wheel (tag commit 6400f0f812b13bc32469e405bd2f762ba3cba7f0), ONNX Runtime 1.31.0 (build commit 402979a), NumPy 2.4.4, and ml-dtypes 0.6.0. The CPU extension linked the wheel’s libraries with matching ONNX_LIGHT_CPU_PYTHON_STABLE_ABI=OFF.

All four reported gaps reproduced twice before optimization. Measurements used the exact registered com.microsoft::GroupQueryAttention benchmark models and inputs, not replacement workloads. Both backends used one thread, affinity CPU 0, 100 warmups, and 1,000 measured iterations per case, with a three-second cap that was never reached. The existing benchmark CLI measures the CPU phase before constructing ORT, then measures ORT; it does not alternate individual samples. CPU feeds were backend tensors, ORT feeds were NumPy arrays, and recording was disabled during timing. ORT used sequential execution and one inter-op thread. Spin defaults were unchanged: onnx-light resolved adaptive spinning with 10,000 iterations and ORT retained its default spinning. With one effective thread neither has idle workers to spin. Compilation and profiling did not overlap timed runs.

Short grouped prefill was paying packing and GEMM setup costs for every 16-row query tile. AVX2/FMA now uses up to 32 rows for causal rank-three grouped attention with query/KV lengths at most 64 and both head dimensions 64. The executor, input conversions, accumulation precision, and softmax are unchanged. A 64-row experiment was rejected: GQA FP32/FP16 measured 0.439922/0.430304 ms versus 0.419815/0.398470 ms for the corresponding 32-row experiment without the safety scan.

Wider tiles evaluate additional masked products. An invocation-local vectorized V check retains the original 16-row tiles for NaN/Inf and unsafe FP32 magnitudes, preserving earlier causal rows that must not acquire zero-times-NaN/Inf. BF16 retains its old tile size. The check is inside the measured call, does not cache input contents, and adds no scratch allocation. Execution telemetry reports the actual tile size, including fallback.

Callgrind 3.22.0 profiled ComputeAttentionFloat32Streaming.SmallCausalGqaCapsWorkerCount repeated 20 times. Original versus final QK GEMM and transpose-packing calls fell from 1,280 to 640 each. Transpose-packing instructions fell from 2,901,760 to 1,840,000; the final finite-value scan ran 20 times. AVX2/FMA microkernels and softmax were present in both profiles. Wider tiles do more masked arithmetic, so total instructions increased: this is an amortization/latency improvement, not a FLOP reduction. These native-test profiles include data generation and assertions and are not end-to-end phase percentages. Hardware perf events were blocked by perf_event_paranoid=4.
