Binary Kernel Design#

Nineteen binary ONNX operators share one descriptor, broadcast-plan, and runtime-adapter architecture. The implementation is under ml_cpu_compute/src/math/binary and the registered adapter is onnx_light_cpu/kernels/elementwise/binary_kernel.cc.

Prepared execution#

NodeProto
   |
   v
BinaryOperationDescriptor
(operator, opset, attributes, typed adapters)
   |
   +---- concrete input shapes and types
   v
BinaryBroadcastPlanCache (8-entry LRU)
   |
   v
immutable BinaryBroadcastPlan
(output shape, coalesced strides, loop family)
   |
   v
scalar or bulk typed function

BinaryOperationDescriptor is built once for the node. It validates operator-specific attributes such as Mod.fmod and BitShift.direction, resolves the output type, and binds scalar and optional bulk functions for the exact input/output type triple.

Dynamic shapes use a bounded eight-entry LRU cache. Its key contains a monotonic descriptor identity, input/output types, and both shapes; it never stores raw descriptor pointers. A miss constructs and validates a fresh plan, so stale strides cannot be reused.

Operators and traversal#

The manifest covers arithmetic (Add, Sub, Mul, Div, Mod, Pow), comparisons, logical operators, bitwise operators, BitShift, and PRelu. It is the source of truth for registered type signatures.

Mod tracks schema version 28 while retaining minimum opset 10 compatibility. Starting at opset 28, floating-point fmod=0 uses floor-remainder semantics: nonzero results and exact zeros take the divisor’s sign. The implementation adjusts std::fmod rather than forming a potentially overflowing quotient. fmod=1 retains truncated-remainder semantics, including the dividend’s signed zero. Earlier opsets still require fmod=1 for floating-point inputs. FLOAT16 and BFLOAT16 use the same scalar semantics through the existing SIMD-capable float conversion adapters.

After right-aligning shapes, the plan assigns zero strides to broadcast dimensions, removes unit dimensions, coalesces compatible adjacent dimensions, and selects one loop family:

Loop family

Purpose

Contiguous

Both inputs and the output advance linearly.

Left / right scalar

Broadcast one scalar while preserving operand order.

Repeated contiguous block

Reuse one broadcast value or block across a contiguous suffix.

Inner-vector / outer broadcast

Vectorize a contiguous inner region while advancing coalesced outer offsets.

General strided

Use the validated coalesced strides as the correctness fallback.

Offsets advance incrementally across outer blocks; division and modulo are not performed for every output element. Empty dimensions produce no work and read neither input.

Compute, scheduling, and safety#

Same-type common signatures bind bulk contiguous and scalar-broadcast kernels. Other legal signatures use typed scalar adapters. Validation occurs before unchecked loops for integer division, modulo, shifts, and other operations with invalid inputs. Comparison results and logical tensors use one byte per BOOL.

The tuning snapshot has separate thresholds for bulk, block-broadcast, and scalar layouts plus a target block size and participant limit. Independent flat ranges or outer blocks are submitted through the session executor; the plan itself owns no scheduler and stores no thread count.

An input may alias the output only when its type and shape equal the output and the selected traversal cannot overwrite a value before its final read. A broadcast input is never expanded in place.

Float32 Greater on AVX2#

Greater binds its float32 contiguous bulk callback to an AVX2 implementation when both compilation support and runtime CPU/OS support are present. The same callback handles contiguous suffixes of row broadcasts. Four eight-element ordered comparisons are packed into 32 bytes, reordered across the 128-bit lanes, and masked to canonical BOOL values (0 or 1). Eight-element and scalar tails never read or write beyond the range. NaNs compare false. Other types, scalar broadcasts, general strided loops, and non-AVX2 builds retain their existing implementations. Dispatch is resolved at descriptor construction, not inside each row, and scheduling is unchanged.

Float32 Less on AVX2#

Less uses the same packed float32 comparison implementation as Greater, with operands reversed, for contiguous, left-scalar, and right-scalar bulk callbacks. Reversing operands rather than negating a comparison preserves ordered IEEE semantics: NaNs compare false, including in scalar broadcasts and tails. Descriptor construction checks compilation and runtime AVX2 support. Other types, general strided loops, scheduling, and non-AVX2 fallbacks are unchanged.

Bool Or on AVX2#

Or resolves contiguous and left/right-scalar callbacks once when constructing the descriptor. AVX2-capable builds and CPUs use unaligned 32-byte loads, bitwise OR, a zero comparison, and masking to canonical BOOL bytes (0 or 1). Noncanonical nonzero input bytes remain true. Scalar broadcasts load the scalar once: true fills the output with ones without reading the vector; false normalizes the vector. Short ranges and tails stay within the input/output buffers, and exact vector/output aliasing is supported. Other CPUs retain the existing portable bulk callbacks. Broadcast traversal, scheduling thresholds, executor ownership, and input generation are unchanged.

Bool And on AVX2#

And also resolves contiguous and left/right-scalar AVX2 callbacks once at descriptor construction. Each 32-byte vector compares both inputs against zero, ORs the zero masks, then uses AND-NOT with ones to produce canonical BOOL bytes. A bitwise AND of the input bytes would be incorrect for noncanonical true values such as 2 and 128. A false broadcast scalar fills the output with zeros without reading the vector; a true scalar normalizes the vector. Empty ranges return before reading either input. Unaligned buffers, scalar tails, and exact vector/output aliasing are supported. The portable callbacks, broadcast traversal, executor scheduling, and tuning thresholds are unchanged.

Float32 Div beyond last-level cache on AVX/AVX2#

Out-of-place contiguous float32 Div can use non-temporal AVX stores when the executor exposes one thread and the two inputs plus output exceed both 32 MiB and the detected last-level cache capacity. Unknown cache topology, AVX-512, smaller tensors, in-place outputs, scalar/row broadcasts, and parallel execution keep their existing paths. Selection uses the whole tensor extent, not a benchmark name or input values. Cached topology and SIMD detection keep CPUID out of the inner loop.

The kernel still uses correctly rounded vdivps, not a reciprocal approximation. A scalar prefix aligns output to a 64-byte cache line; four vectors fill two complete cache lines per iteration, followed by a scalar tail. Unaligned input loads are supported. sfence completes streaming stores before returning to the runtime or a dependent operator.

Float32 Add beyond LLC on AVX2#

Large, out-of-place, single-thread contiguous float32 Add now shares the streaming-store loop and eligibility check used by Div. The three-array footprint must exceed both the detected L3 size and 32 MiB; unknown topology, AVX-512, parallel execution, in-place execution, scalar broadcasts, and row broadcasts retain their cached-store implementations. Inputs may be unaligned. The loop aligns the output to a cache line, streams complete 32-element blocks, handles the remaining elements without overreading, and fences before return. The arithmetic remains ordinary IEEE-754 addition.
