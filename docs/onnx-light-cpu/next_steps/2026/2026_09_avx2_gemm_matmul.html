AVX2 FP32/FP64 GEMM and MatMul Gap Closure#

Date:

2026-09

Updated:

2026-10-26

in progress

This September report also includes an October 2026 MatMul follow-up (#988) with updated measurements and implementation decisions.

Objective#

Issue #633 asks for the dominant AVX2 FP32/FP64 Gemm/MatMul gaps against ONNX Runtime to be measured and closed under an -DONNX_LIGHT_CPU_MAX_SIMD_LEVEL=AVX2 ceiling build, covering square, transformer-projection, batched, skinny-M, skinny-N, large-K, transpose, bias, dynamic-B, and N=1..7 tail cases, without touching AVX-512 dispatch/heuristics or compact/Attention code.

Baseline methodology and its sandbox limitation#

tools/benchmark_gemm_parity.py is the canonical parity gate, but it imports onnx_light (the sibling onnx-light checkout) to build the reference graphs and run the ReferenceEvaluator/kernel-usage instrumentation. That checkout is not available in this sandbox, so the canonical gate could not be executed here. To still gather evidence, this pass used two independent, narrower substitutes on an AVX2+AVX-512-capable 4-core host:

  • An AVX2-ceiling Release build (-DONNX_LIGHT_CPU_MAX_SIMD_LEVEL=AVX2 -DONNX_LIGHT_CPU_WITH_ONNX_LIGHT=OFF) linked into a standalone timing harness that calls GemmFloat32/ GemmFloat64 directly (no onnx-light dependency), covering the priority shape corpus from tools/benchmark_gemm_parity.py at one thread and with a naive per-call thread-spawning executor standing in for the “available physical-core policy”.

  • A plain onnx + onnxruntime (pip) Python script building single-node Gemm graphs and timing InferenceSession.run with intra_op_num_threads=1 for the same shapes.

The important caveat: upstream ONNX Runtime has no supported way to cap its own CPU execution provider to AVX2 at runtime (confirmed - this would require rebuilding ONNX Runtime with AVX-512 disabled at compile time). This host supports AVX-512, so the ORT numbers below reflect ORT’s AVX-512 MLAS kernels, not an AVX2-vs-AVX2 comparison. Any gap on square/wide-projection shapes below is therefore expected to include a genuine ISA-width component (8 vs 16 lanes) that this issue explicitly excludes from scope (“do not change AVX-512 dispatch”). Closing that portion would require either a genuinely AVX2-only host or an ONNX Runtime build with AVX-512 compiled out, neither of which this sandbox provides.

The single-core AVX2 microkernel (GemmMicroTile_AVX2FMA_F32Impl/ ...F64Impl in ml_cpu_compute/src/math/gemm/avx2/gemm_avx2_fma.cc) already reaches roughly 78-80% of this host’s theoretical AVX2 FMA peak (2 FMA ports x 8 lanes x 2 flops/FMA) on square/projection/transpose shapes, and the float64 path shows the same efficiency against its own peak. GEMV-like skinny_m/skinny_n shapes are memory-bandwidth bound (streaming the full B/A operand once) and already reach or exceed the measured ORT number; split_k and direct/tiny_dynamic (call-overhead-dominated tiny shapes) are already ahead of ORT here. The remaining gap is concentrated in square/projection/transpose shapes and tracks the AVX2-vs-AVX-512 lane width, not an under-tuned AVX2 code path: register blocking (kGemmAVX2MR = 6 rows x 16 columns), K-unrolling by 4, prefetching, and per-microarchitecture register-row selection (Intel Core vs AMD Zen, see SelectGemmRegisterRowsForMicroarchitecture in ml_cpu_compute/src/math/gemm/gemm_blocking.cc) were already in place before this pass.

A naive multi-thread scaling probe (thread-per-call executor, 4 physical cores) showed close to 2x scaling on square_1024/transformer_projection (consistent with a partially memory-bandwidth-bound workload on this host) and a regression for very small shapes such as square_128 whose serial runtime (about 47 microseconds) is smaller than the thread-creation/join cost of the naive harness executor. That regression is judged to be a benchmark- harness artifact (the real embedding runtime supplies its own persistent thread pool, and SelectGemmParticipantCount already caps square_128 at 2 participants, not 4) rather than evidence of a fixable admission-control bug, so no participant-limit change was made without a persistent-pool measurement to confirm it.

Status#

No AVX2-specific microkernel, packing, blocking, or scheduling change is included in this pass: the measured evidence available in this sandbox does not demonstrate a fixable AVX2 regression separate from the AVX2-vs-AVX-512 lane-width difference, and the issue’s own instruction is to “optimize only bottlenecks demonstrated by the baseline.” test_gemm_kernel and test_gemm_plan continue to pass unchanged under the AVX2 ceiling build.

Remaining work requires the dedicated-machine setup used by prior roadmap items (see the Gemm/MatMul roadmap): an onnx-light checkout to run tools/benchmark_gemm_parity.py directly, and either a genuinely AVX2-only host or an ONNX Runtime build with AVX-512 compiled out, so the reported ratios reflect an AVX2-vs-AVX2 comparison instead of AVX2-vs-AVX-512.

October 2026 MatMul follow-up (#988)#

The investigation above describes the September pass, not the current implementation. On 2026-10-25, the eight cases in issue #988 were remeasured on an AMD EPYC 7763, which supports AVX2/FMA/F16C but not AVX-512. All eight gaps reproduced in both pinned baseline campaigns below. An unpinned two-thread run did not reproduce the FP32 128-square gap, illustrating why the original dashboard numbers cannot be treated as a stable baseline.

Environment and protocol#

  • Shared Linux VM: four logical processors, two physical cores; process affinity restricted to logical CPUs 0,2 (one sibling per core) for both backends. This is still a shared runner, not dedicated hardware.

  • Original parity campaign: onnx-light-cpu 0.2.0 baseline production sources 86c8762be5bb0c01459c1998f5daf8dc70e268fa; optimized sources 83952ac5da670ddeb7431565f3c5e87f5d967d90. These Python/ORT timings predate the rejected paired-row implementation (232b1ca5f1050b144d40129770d2b499d42b5c97), so their skinny-N entries are historical results, not gains retained by this PR. Both builds used GCC 13.3.0, CMake Release, and ONNX_LIGHT_CPU_MAX_SIMD_LEVEL=AVX2. Runtime detection returned 3 (AVX2); the throughput driver reported AMD Zen, FMA, and six register rows. The baseline was rebuilt in the same build tree after verifying its two production files against the baseline revision; no second runtime build was loaded alongside it.

  • ONNX Runtime 1.31.0, official CPython 3.13 Linux wheel, Release build, reported commit 402979a; CPUExecutionProvider only.

  • onnx-light 0.2.0, official release wheel onnx_light-0.2.0-cp313-cp313-manylinux_2_27_x86_64.manylinux_2_28_x86_64.whl. Release tag commit: 6400f0f812b13bc32469e405bd2f762ba3cba7f0; the wheel does not report a compiled source commit, so the tag alone is not proof of binary provenance. Its loaded core library SHA-256 was 181a18f807267481b5006060f6fbe6a05cafe3ce8dea75f90f5fb44c9d59741a. The CPU extension linked to the wheel’s exact core/proto/thread libraries with ONNX_LIGHT_CPU_PYTHON_STABLE_ABI=OFF.

  • Python 3.13.16, NumPy 2.5.4. Inputs came directly from the existing named backend cases (seeds 433/434), with both matrices dynamic. CPU feeds remained native backend tensors; only ORT feeds used NumPy.

  • Separate runs at one and two explicitly configured intra-op threads. ORT used sequential execution and one inter-op thread. Neither backend pinned individual workers; both inherited the same process affinity. Spin settings were unchanged in every campaign: onnx-light’s adaptive policy (default 10,000 spin iterations), ORT’s default spinning enabled. These are backend defaults, not identical spin budgets; the one-thread measurements avoid worker-spin effects.

  • Two fresh CLI processes per revision and thread count; each case used 20 warm-ups and 101 measured calls, with a 10-second cap that did not truncate the measurements. Tables show the two independent per-process medians in milliseconds. The ORT column spans its medians across all four before/after processes, exposing reference-backend drift.

  • The standard backend CLI measures CPU first, then constructs and measures ORT. That order was identical before/after. The isolated AVX2 parity worker was attempted but rejected by this onnx-light wheel before timing because its deserialized input wrappers were not accepted as tensors.

Reproduction#

Configure the existing source-integration build against the installed onnx-light runtime, with Release, tests enabled, the AVX2 ceiling, and matching Python ABI. Build _cpuregister, _cpukernels, gemm_throughput, test_gemm_kernel, test_gemm_plan, and test_onnx_light_matmul_kernel using cmake --build with --parallel 48. With the source checkout on PYTHONPATH, run the following twice for each revision, changing the output prefix each time:

The standalone C++ gemm_throughput driver was therefore used to measure the paired-row kernel in isolation, not as an end-to-end or ORT comparison. Findings and validation#

Hardware-counter profiling was unavailable (perf_event_paranoid=4). Disassembly of GCC’s six-row FP32 microkernel showed twelve accumulator-array stores inside each four-step K iteration. Named accumulators remove that repeated array writeback. The retained epilogue consumes those accumulators directly through compile-time-unrolled row stores, without intermediate arrays. The same microkernel serves converted FP16 square panels. No reduction-order, packing, or FP16 conversion change was needed for these squares.

Skinny-M improved by limiting FP32’s row slab to four rows and increasing contiguous column slices up to 1024 columns while retaining enough tasks for the executor. The FP16 slab remains unchanged. A wider-column-only experiment was not sufficient; it was not retained without the shallow-slab improvement. The original optimized skinny-N kernel shared each B vector across four A rows with two reduction chains, but changed finite-input cancellation behavior. The subsequent paired-row implementation preserved the original four-chain reduction while sharing B across two rows, but regressed the measured workload. Neither skinny-N optimization is retained.

Relative to the mean of the two baseline medians, square-case improvements range from 1.21x to 1.45x, and skinny-M from 1.48x to 2.40x in the original parity campaign. Its 1.41–1.74x skinny-N result applies only to revision 83952ac5 and does not apply to the retained implementation. The follow-up isolated C++ measurements above show 0.93x at both thread counts on a different shared VM; they are not comparable to the original Python/ORT campaign and do not establish end-to-end parity. They motivated restoring the original skinny-N kernel rather than retaining a measured regression. Remaining ORT advantages in the original campaign include the larger squares, two-thread FP16 128-square, and two-thread skinny-M. The original historical latencies were not reproduced exactly, and their thread/build provenance remains unknown.

After restoring the single-row kernel, the AVX2 build passed 100 GEMM kernel tests, 49 plan tests, and seven MatMul integration tests on an Intel Xeon Platinum 8480C with GCC 13.2.0. Unsupported AVX-512/AMX cases were skipped. The original parity campaign passed 99 GEMM kernel tests, 49 plan tests, and seven MatMul integration tests; unsupported AVX-512/AMX cases were skipped. Added coverage includes all FP32 microtile row counts and accumulation modes, unaligned column ranges, vector/K tails, skinny-N special values and cancellation, ignored NaN bias, and skinny-M executor limits at panel boundaries. All eight exact benchmark inputs also matched onnx-light’s built-in kernels at one and two threads, with reference outputs computed before CPU-kernel registration (FP32 rtol=atol=1e-4, FP16 rtol=atol=1e-2).

October 2026 Gemm follow-up (#981)#

This follow-up measures the 36 exact dynamic-input cases in issue #981 on 2026-10-26. It does not reuse the issue’s historical timings as a baseline. The baseline production sources are revision 64961c5 (also unchanged in 30cd15e and 3ecf02b), which already contains the MatMul follow-up above.

Environment and protocol#

  • AMD EPYC 7763 shared Linux VM, four logical CPUs on two physical cores. Both backends inherit process affinity 0,2. This processor has AVX2/FMA/F16C and no AVX-512; CPU dispatch reports SIMD level 3.

  • GCC 13.3.0, CMake Release, ONNX_LIGHT_CPU_MAX_SIMD_LEVEL=AVX2; onnx-light-cpu 0.2.0, Python 3.13.16, NumPy 2.5.4.

  • ONNX Runtime 1.31.0, official CPython 3.13 Linux wheel, Release, reported commit 402979a, CPUExecutionProvider only.

  • onnx-light 0.2.0, official release wheel named in the MatMul follow-up, extracted outside the checkout and selected with PYTHONPATH. The loaded core library has SHA-256 181a18f807267481b5006060f6fbe6a05cafe3ce8dea75f90f5fb44c9d59741a. The wheel does not identify its compiled source commit. This checkout links its exact core/proto/thread libraries, with ONNX_LIGHT_CPU_PYTHON_STABLE_ABI=OFF matching the wheel.

  • One explicitly configured intra-op thread for both backends; ORT uses sequential execution and one inter-op thread. Spin policies are unmodified defaults, but no worker spinning is involved with one thread.

  • Two fresh CLI processes per case and revision, five warm-ups and 31 measured calls. The 120-second cap is identical throughout. CPU is measured before creating ORT, avoiding its idle worker interference. Tables report individual process medians in milliseconds, not minima.

Profiling and implementation#

Hardware performance counters are unavailable on this VM (perf_event_paranoid=4). Generated-code inspection with objdump -Cd instead identified accumulator spills inside GCC’s four-way-unrolled GemmMicroTile_AVX2FMA_F32Impl<6> depth loop. Its twelve accumulators already provide independent FMA chains; unrolling extends temporary lifetimes enough to spill an accumulator to the stack.

Only the six-row, sixteen-column FP32 microtile now uses a single depth loop. The generated hot loop keeps all twelve accumulators in registers. Smaller row counts retain their original unrolling. The sequence of FMAs for each output, alpha/beta application, bias modes, tail handling, packing, dispatch, executor ownership and allocation behavior are unchanged. AVX2 FP16/BF16 widening paths reuse this FP32 tile; the compact native kernels, FP64, scalar, AVX and AVX-512 implementations are untouched.

The direct microtile test now covers depth boundaries around 8, 16, 128 and 512, for every row count, output tail and accumulation mode, including non-unit alpha/beta, column bias and unaligned output ranges.

Interpretation and remaining gaps#

Comparing the means of the two per-process medians, the cases using the changed tile improve by 1.04–1.11x. Both FP32 and FP16 256/512-square cases without bias move ahead of ORT in both optimized runs. ORT is faster in 28/36 cases in each baseline campaign, versus 15/36 and 13/36 after. These counts use unrounded data, not the displayed decimal values. The largest historical gains (including the 2.22x column-bias result) are not reproduced at this already-optimized baseline.

Only 27 of the 36 historical gaps repeat in both baseline runs. The nine not consistently reproduced are FP32 128-square, skinny-M, large-K-1024, projection decode, both FP16 128-square transpose cases, FP32 and FP16 big_m128_n8192_k128, and FP16 big_m128_n16384_k128. The latter is already substantially faster than ORT before this change.

The two M=1 FP32 cases use an untouched skinny-M path, not this microtile. Their before/after medians fluctuate by about 3–4% in the unfavorable direction; no improvement is claimed for them. Larger residual gaps include FP32 4096-square, large-K and wide/tall matrices, and FP16 tall and large-K matrices. FP32 projection and several bias cases remain near parity or slightly behind. No blanket parity claim is made.

Campaigns were grouped by revision, not alternated between binaries. The per-process medians and ORT ranges expose drift, especially for small and wide cases. The two runs for some tall shapes also differ noticeably. This shared-runner evidence supports the localized spill removal, not a dedicated-machine performance gate or exact reproduction of the dashboard’s unknown thread/build provenance. Multithreaded performance still requires measurement on the target deployment.

Correctness and validation#

The optimized AVX2 build passes 100 GEMM kernel tests (four unsupported-ISA skips), 49 plan tests (two unsupported-ISA skips), 13 Gemm integration tests and all 35 benchmark CLI tests. The added CLI test runs a real big Gemm case and checks its workbook, as well as verifying default exclusion. C++ formatting, Ruff, Black and git diff --check pass.

For an additional exact-workload check, all 36 optimized outputs were saved, the original production loop was rebuilt in the same build tree, and every output byte was compared. All 36 are bitwise identical before and after. The optimized implementation was then restored and rebuilt.

An independent onnx-light built-in oracle was resolved and run for each case before CPU-kernel registration. With the earlier MatMul follow-up’s additional comparison tolerances (FP32 rtol=atol=1e-4, FP16 rtol=atol=1e-2), 33 cases agree. Three FP32 long reductions exceed that additional threshold near zero: 2048-square, 4096-square and big_m128_n128_k8192. The unmodified baseline has exactly the same differences. For example, 17 of 4,194,304 outputs in 2048-square exceed the threshold, with maximum absolute difference among violations 1.4248e-4. This additional oracle comparison therefore does not pass universally; it is not presented as a new regression, nor were tolerances relaxed. Existing correctness requirements and tests are unchanged.
