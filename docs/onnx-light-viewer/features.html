Implemented features#

The viewer inspects ONNX graphs locally with onnx-light. Models are not uploaded. Explicit Convert and Run actions execute installed tooling; inspection does not save or modify the source file.

Available in the viewer#

This overview describes the default branch, not every capability of the underlying onnx-light libraries. Start with the worked example in Getting started; the linked guides explain each control in detail.

Tabs share one compact row, without Navigation/Application headings. The graph name, node/initializer counts and pending-rewriting counter share a single header row. Versions are shown in Status, not above the graph. Model actions remain in the sidebar; application tabs are available without loading a model. See Zoom, navigation and moving nodes.

Click the current graph-name button to choose functions, child subgraphs or pipeline models. The menu also links to parents and remembered sibling subgraphs, without adding another header row.

Opening models#

Open local .onnx, .ort and .pipe-onnx files, bundled demos or public Hugging Face models with persistent caching. See Opening models. No authentication or automatic external weight downloads. Buttons below Model path offer the VS Code file picker and an in-app folder dialog for paths outside the workspace.

Select a remembered local path in Open to see its generation-asset checks, without loading weights or running inference. Mobius exports show whether a pipeline can be assembled, or explain missing assets and unsupported input contracts. Load as pipeline creates a native PipelineProto beside the export, reusing external weights and leaving the original models unchanged, then opens Run → Prompt. Separate embedding/decoder exports and declared past/present caches are connected in C++; onnx-light owns generation and cache feedback. Existing pipelines can be opened directly. Inspection does not reorder history; only a successful open does. These checks do not certify runtime operator support.

ORT models and runtime packages#

A model format is not a package container. .ort contains one ORT FlatBuffer model. Open automatically identifies the expected format from the filename: ONNX protobuf, ORT FlatBuffer, pipeline, encrypted model or package. ZIP archives (.ortpackage or .zip) and directories are supported, including packages with manifest.json, external components, variants and shared assets. Folders are identified as packages without a format selector. Inspect package lists member models; a package with several models may require choosing one. The viewer does not select hardware-compatible variants or apply manifest session/provider options. Native runtimes consume the extracted directory, not the ZIP itself. Package manifests, variants and shared-asset resolution belong to the viewer; onnx-light reads and writes the contained models.

Save → What to save chooses a generic, GenAI or compiled EPContext package. Choose ZIP archive (.ortpackage) or Directory independently of the model serialization: ONNX protobuf, ORT FlatBuffer, or a pipeline. One output field adapts to a file or a new directory. Browse… chooses its name and location; Save copy writes it. There is no separate destination directory or unlabeled file listing. The arrow inside the output field chooses a recent destination without restricting what you can type. New archives contain a version-1 manifest; existing manifests and other assets are preserved, with references updated when the selected model changes format. GenAI and compiled packages require existing configuration/provider assets; Save does not generate tokenizers or compile providers.

ZIP reading/writing is streamed and supports ZIP64. Extraction checks member paths, file types and checksums; links, escaping weight paths and encrypted ZIPs fail explicitly. Extracted assets remain available for recovery and running actions until the panel closes. Save requires a new destination and leaves the original archive unchanged. GenAI generation resolves shared model references through an in-memory configuration overlay, without modifying the original configuration or assets.

Backend catalog#

Search bundled onnx-light cases and inspect their model graphs. See Backend tests; this opens graphs, not a test runner.

Converting models#

Run installed mbext, modelbuilder, Mobius or Olive exporters with visible commands, live output, cancellation and a saved reproduction script; open their output. See Converting models. Requires Python and a trusted workspace; exporter packages and checkpoints are not installed automatically.

Olive export, quantization and recipes#

Export a Hugging Face model ID or local checkpoint to ONNX with Olive, optimize an ONNX model, or select a model-specific recipe. Configure precision, CPU/CUDA target and advanced export parameters. Local-only ONNX quantization remains a separate workflow. The recipe catalogue is cached by Git commit, retains version-pinned entries and shows their required Olive version. See Converting models.

Navigation#

Zoom, pan, area zoom, readable-size views, multi-selection, dragging and sidebar node/operator search with live suggestions. See Zoom, navigation and moving nodes. Moving a node changes only its display position.

Connections attach left-to-right in each node’s input and output order. Repeated inputs have separate entry points; empty outputs keep their slot as a short, unlabeled line below the rectangle.

Carried-result names are longer, with complete hover information. Nearby edge labels stagger when space permits.

Running a model#

Open Run next to Tensors, then select its Run subtab for regular CPU inference with onnx-light or ONNX Runtime. The Prompt subtab preserves language-model generation. Regular execution uses the current model, including unsaved edits; for a pipeline, choose a stage in Model.

Choose an Engine and its logging settings: onnx-light verbosity, or ONNX Runtime severity and verbosity. Each engine retains its own values while switching. ONNX Runtime requires onnx, numpy and onnxruntime in the Python environment selected in Settings → App; onnx-light uses the bundled native SDK. Settings opens the selected engine’s regular Run logging controls, not Prompt-only options. Changes apply to the next execution and unload any retained Run session; Back returns to the Run subtab with the same controls and values. Check Keep session loaded between runs to reuse the actual model session with either engine. Inputs are read or regenerated on each execution, including changed dynamic dimensions. The status distinguishes a newly created session from a reused one and says whether it is still loaded. Unload session, unchecking the option, changing engine/logging/model/stage, cancellation or an error releases the retained session. With the option off (the default), sessions are recreated and released for every run. Initialization time is separate from execution time.

With ONNX Runtime selected, check Enable profiling before Run model. Set Repetitions (1–100, default 1) to execute the same inputs repeatedly in one session. Execution time is the mean per repetition; outputs are from the last. The results plot total kernel time by node and operator across all repetitions, and show timings sorted slowest first: node, operator, execution provider, call count and total milliseconds. These are the runtime’s optimized nodes, which may be fused rather than match the original graph. Profiling adds overhead and always creates and releases a fresh session, even if session reuse was previously selected. Turn profiling off to use session reuse again. Save profiling trace… exports the complete Chrome trace JSON, including session initialization and execution events, for a compatible timeline viewer. The trace stays available until the next run or model change; temporary profiling files are removed after execution.

Every symbolic or unnamed dynamic dimension needs an explicit non-negative size. Shared symbolic names use one field; unnamed dimensions are labeled input:axis. For each input, choose Random (SDK-generated normal samples), TensorProto file (.pb) (inline binary protobuf, selected with Browse…) or Tensor text. Random generation requires a tensor with known rank and an SDK-supported element type; SDK errors are shown without a fallback. File tensors are bound to the selected input name. For text, a three-element float input named X is float[3] X = {-1, 0, 2}; its concrete shape must match the dimension fields. Integer values are parsed natively without JavaScript rounding. A trusted workspace is required. Load input (.pb)… is always visible next to each input source and automatically switches that input to file mode. Use it to reload a saved input exactly, including integers beyond JavaScript’s exact-number range. Random inputs are otherwise regenerated on every run. Run model displays execution time and actual input/output type, shape and values for tensors up to 32 elements. Larger tensors show metadata only. Native errors appear in the status; engine logs appear below it. Set onnx-light’s Logging verbosity above zero to see SDK stdout/stderr and execution events. Neither engine modifies the graph. ONNX Runtime and verbose onnx-light runs execute temporary snapshots that are removed after execution.

For each executed tensor, Statistics opens SDK summaries, quartiles, histograms and a heatmap without running the model again. Save statistics… exports the summary as JSON; Save tensor… exports the full inline TensorProto (.pb), including values omitted from the preview. Saved tensors can be reused as file inputs. Each save asks for a destination and can be cancelled. A new run or model change invalidates the previous run’s tensors. Non-tensor outputs have no tensor inspection or save controls; unsupported statistics show the SDK error.

Running language-model prompts#

After conversion, open Run → Prompt next to Tensors. Select onnx-light or onnxruntime-genai (when a GenAI configuration is available), edit the prompt and choose a maximum number of new tokens (default: 32). Requires a trusted workspace and a causal language model. Both ONNX engines execute in C++, in an isolated Node process so cancellation can stop native execution. Execution uses the saved model, not unsaved graph edits.

The bundled onnx-light SDK supplies its CPU kernels. Native tokenization for both engines uses the ONNX Runtime GenAI C API (0.17.0 or newer), not its Python module. The tokenizer directory must contain genai_config.json and tokenizer assets (tokenizer.json or tokenizer_config.json with its referenced files). For onnx-light, it must also contain a causal-model config.json. Discovery prefers a complete recorded source package, then the export directory; a bare Hugging Face checkpoint without genai_config.json is not a native tokenizer package. ONNX Runtime GenAI requires its package beside the exported model. Install the matching C++ GenAI and ONNX Runtime libraries and set ONNX_LIGHT_VIEWER_GENAI_LIBRARY to the absolute GenAI shared-library path before starting VS Code. Set ORT_LIB_PATH to the absolute ONNX Runtime shared-library path when it is not already discoverable. Choose CPU/CUDA libraries compatible with the exported configuration; the viewer installs neither. Only Hugging Face validation needs torch, transformers and the original cached checkpoint in Settings’ Python environment.

Conversion saves source information next to each exported model. Validate with Hugging Face uses that source checkpoint and the same generated prefixes to compare logits, rather than comparing unrelated divergent continuations. Output text, token IDs, raw-logit scores and reference results share one column per generated token. Each column includes maximum absolute and relative error, L2 distance, and counts of vocabulary coefficients with absolute differences below 0.01, 0.1 and 1. Runtime errors are shown without substituting another engine; Cancel stops execution.

With either onnx-light or onnxruntime-genai, token columns appear as soon as the C++ engine produces them. Each column includes its phase and latency in milliseconds. The first token is Prefill; subsequent tokens are Decode. The summary shows prefill time and the mean of decode tokens only; a one-token result has no decode mean. Hugging Face validation also reports per-token timings, using the prompt once and the exported token prefixes with its decode cache thereafter. GenAI timings include inference and CPU logit transfer. onnx-light’s SDK observer measures per-iteration input preparation, embedding execution, inference and token selection; it excludes per-call session construction, snapshot copying and callback work. Neither engine includes loading, tokenization, detokenization, retained-logit serialization or UI rendering in these token timings.

Model loading and warmup have separate timings. On each new native session, warmup uses the first prompt token alone and generates one token; the real run starts with a fresh generation/cache state. HF validation also measures loading and a one-token warmup forward separately. Native loading covers runtime, tokenizer and model/session initialization, not viewer preflight discovery or prompt encoding.

Keep the current model loaded is optional and off by default to avoid unnecessary memory use and swapping. A retained session reports its original loading/warmup times as initial timings, not costs paid again. Unload model now, cancellation, changing models/engines/settings and closing the panel release it. One panel retains at most one native model; keeping it during HF validation can hold two models in memory.

Select the engine on Run → Prompt, then open Session settings to jump to its subtab in Settings → Engine. Controls preserve defaults unless changed and never edit the exported configuration. GenAI’s - uses the exported configuration, or the engine default when the option is absent from that file. onnx-light exposes allocation capacity, logging and native kernel profiles. GenAI exposes graph optimization, memory options, prepacking, graph execution mode, log ID/verbosity, custom operator libraries and ORT profiling. Unsupported providers/options raise runtime errors, without switching engines.

Settings → Engine → onnxruntime lists each option, a compact value control and its explanation in three columns. Session configuration entries already lists the keys: choose a value or fill in its value field, without entering option names or JSON. Blank values preserve genai_config.json and runtime defaults; clearing a value removes its override. For example, select 0 - No for session.intra_op.allow_spinning to reduce idle CPU use. See the ONNX Runtime configuration keys for runtime-version requirements. Invalid values block generation; unsupported runtime options are reported on Prompt. Device controls choose providers and GPU settings; Use providers from genai_config.json preserves the exported provider selection.

Open Generation settings from Prompt, or Settings → Generation, to set Temperature (default 0, greedy decoding) and Maximum new tokens (default 32, range 1–4096, excluding input tokens). Positive temperatures enable SDK sampling in either engine; EOS can stop generation before the limit. These viewer-local values apply on the next run without changing exported files or unloading a retained session. HF validation remains an argmax/logit comparison at the generated prefixes, not a second sampled sequence.

onnx-light loading, shape checking and intermediate release use their defaults; these controls are not exposed in Settings. GenAI exposes initialization/prepacking and session-thread controls, not a separate parallel weight-reader thread count. Parallel graph execution is not parallel loading. Profiles add overhead and are written under .prompt-profiles beside the model.

With onnxruntime-genai, use Repetitions (1–100, default 1) to generate from the same prompt repeatedly in one session, resetting generation state each time. Only the last repetition’s tokens, timings and HF comparisons are displayed; sampling may produce different tokens across repetitions. Enable Profiling directly on Run → Prompt or in Settings → Engine. A profiled run creates a fresh session and unloads it automatically to finalize the trace, regardless of Keep the current model loaded. Results plot total kernel time by node and operator, including the one-token warmup and all repetitions. Each profiled run has its own directory under .prompt-profiles.

onnx-light 0.2.3 uses the SDK’s synchronous GenerationOptions.on_step observer for live tokens, genuine per-token timings and bounded raw last-position logits. FLOAT, DOUBLE, FLOAT16 and BFLOAT16 outputs support raw scores and the same token-aligned HF vocabulary comparisons as GenAI. If the capture budget is exhausted, tokens and timings continue, while unavailable scores/comparisons are identified explicitly. No timings are estimated by dividing the total runtime. The onnx-light engine accepts eos_token_id as a non-negative integer or a list of non-negative integers in generation_config.json or config.json. Generation stops on any listed EOS ID; an empty list disables EOS stopping. Native pipeline generation uses the SDK’s PipelineProto overload; unsupported stages or inputs fail explicitly, without a viewer-side generation loop. With the owning loader, the SDK’s LoadedRuntimePipeline overload uses explicit generation options: the viewer’s token limit and temperature replace stored sampling settings, while pipeline interface names and EOS defaults are preserved.

Inspection#

Inspect types, symbolic shapes, attributes/schema defaults, dense/sparse/encoded initializer metadata, opaque/structured types, bounded previews and Markdown operator documentation. See Operator and tensor inspection. External or omitted payloads are not read for previews; this is not a full tensor-data browser.

Tensor statistics#

Open the statistics icon on a node, beside an inspector tensor, or in Tensors. Use Previous tensor / Next tensor without closing the dialog. From Tensors, navigation follows the filtered list across pages; from the inspector, it follows the current scope’s stored tensors. Browse mean, median, extrema, quartiles, shape/dtype, a histogram and a square color map. Low-bit numeric tensors and SDK-supported encoded quantized weights are supported. See Operator and tensor inspection.

Stored tensor distributions#

The Tensors tab groups stored weights and constants by type and shape, showing tensor counts, elements and theoretical logical bytes. Dense, sparse and encoded values stay separate; unknown sizes remain explicit. No payload reads, decoding or execution are needed for these totals. See Operator and tensor inspection.

Subgraphs and functions#

Browse graph/list attributes, captured inputs, model-local function definitions and nested graphs with breadcrumbs. See Subgraphs. Function bodies are definitions, not specialized executions of the selected call.

PipelineProto#

Navigate stages and generation-settings previews, run per-stage inference and fusion, and save whole containers with embedded or external weights. See Opening models. No pipeline execution or encryption.

Shape/type inference#

Open Symbolic and choose Refresh shapes for visible update counts and refreshed labels without resetting the camera or selection. See Operator and tensor inspection. In-memory only; unsupported operators may fail.

Symbolic dimension names and equalities#

Open Symbolic → Make dimensions equivalent to list distinct symbolic dimension labels, including nested graphs, functions and pipeline stages. Select a dimension, then its destination, or drag it to the right of the equals sign on the line of the name to keep. Choose Apply replacements to update the names throughout the model, including in dimension expressions. Only declare an equality you know is valid for your model.

Choose Shorten dimension names to remove a common namespace prefix, such as component.model.. Both actions edit the model, preserve the edit through Unfuse, and require Save to keep the changed labels on disk. No weight payloads are read during renaming. See Operator and tensor inspection.

Static metadata#

Inspect constants, tags, lifetimes, last reads, releasable/unused outputs and stored model/graph/node/tensor metadata. See Metadata and lifetimes. This is static analysis, not measured runtime memory usage.

Statistics#

Open Statistics to refresh complete-model counts, operator/type distributions and referenced file sizes, independently of nested navigation.

Memory profiling#

Set dynamic dimensions and view the estimated CPU memory curve with paginated per-node allocation/scratch events. Zoom for more operator labels and hover for numerical and symbolic allocation details. See Memory profiling without execution. Native estimation, not model execution or measured RAM/GPU usage.

Estimate again with different dimensions to overlay configurations on shared scales. Select a configuration for inspection, or remove it from the comparison.

The matching Model graph shows reported in-place reuse as background port links.

Compare models#

In Rewritings, open Compare and choose a target model to inspect the onnx-light rewriting diff from the entire current model, including unsaved edits. Expand a step to see its before/after nodes and attribute previews; initializer positions refer to the graph immediately before that step. Node moves and function and opset declarations are listed separately. Neither model is changed.

The SDK requires compatible model interfaces and existing opset imports, and may reject other unsupported changes. Pipeline containers are not supported. An empty plan is not a byte-for-byte equality check: some metadata is outside the SDK comparison. Comparison restores omitted inline weights and may read external weights, so time and memory can grow with model size. External weights require local model paths; payloads are not sent to the webview.

Optimizer backends#

In Optimize, choose onnx-light for native pattern selection or onnxscript for Python optimization and fusion. ONNX Script requires a trusted workspace and onnx and onnxscript in the configured Python environment. Both operate on the current in-memory model, not the source file. ONNX Script output appears below Run global optimization after completion, including node and Identity counts before and after each stage. Changed Python results cannot be unfused and clear earlier native undo history. See Fusion patterns.

With onnx-light, inspect Matched patterns, undo the last operation or choose Back to original model without leaving Optimize.

Pattern groups#

Combine Default, L1, L2, Layer, onnx-light-cpu or All in Fuse or Optimize, even when their members overlap, then refine individual patterns. Fuse selects only graph-applicable members; Optimize starts with Default and leaves the opt-in RepeatedLayer unchecked. All includes it. See Fusion patterns. Choosing groups alone does not transform or save the model.

Native fusion matching#

In Fuse, select patterns and click Run Matching. Inspect the Before and After candidates, check compatible matches, then click Fuse selected. Previewing does not modify the graph. See Fusion patterns.

Model partitioning#

Open Rewritings → Global Rewriting, choose RepeatedLayer or PartitionGroup under Operation, then click Apply. The SDK replaces matched regions with model-local function calls. Click a node’s Function link to inspect its body.

Unfuse Last undoes the operation; Save keeps a copy of the result. Partitioning changes the in-memory graph, not the source file, and does not export separate model files. See Fusion patterns.

Patterns from node selections#

Select connected operators, right-click the selection and choose Create / edit FunctionPattern… to create a FunctionPattern in a popup. Inspect and copy its function text. Match and fuse occurrences across the model, undo with Unfuse, or opt into the new Selection patterns optimization bucket. Edit the match and replacement functions in SDK textparser syntax, then Apply edits. The Patterns page lists created templates across models: edit them there, Save patterns… to a portable library file, and Restore patterns… in another viewer session. Restoration merges definitions and asks before replacing existing ones; invalid files leave the library unchanged. The popup also lists existing ONNX functions under Patterns / model functions: edit Function body, then Apply edits to update every call and Save to persist the change. See Fusion patterns.

Unfuse (undo native edits)#

Choose a saved rewriting in the dropdown between the graph name and node counts. None is the default and displays the original graph. Selecting a name applies that alternative and opens its ordered steps in Rewritings; selecting None again restores the original graph without a pending replay. Switching alternatives replaces current native fusion edits, not the source file.

Open Rewritings to undo native edits without changing the source file. Unfuse last reverses one complete operation: a batch of selected matches, a global optimization, a global pass or an applied rewriting-scenario step/batch. Repeat to go back further, or choose Unfuse all to undo all available operations, including those on other pipeline stages. The history lists operations newest first; click a match to highlight its surviving result nodes. These controls are disabled when no undo history remains. See Unfuse and rewriting plans for history and saved rewriting-plan details.

Optimization results count original impacted nodes, not surviving result nodes. Expand Before / after this operation to inspect the edit, including deleted operators and initializer-only changes. Pattern buttons highlight current surviving results separately.

The native Optimize panel also offers Unfuse last and Back to original model (undo all). Changed ONNX Script results cannot be undone and clear earlier native history; later native edits undo back to that Python result. Saving does not persist the session’s undo stack.

Settings by category#

Open Settings → App to configure download and Python paths, sidebar width and visible viewer panels, or reset viewer preferences. Open Settings → History to inspect cache locations and remove or clear Open, Save and conversion suggestions. Clearing history never deletes files. Open Settings → Device to select devices independently; CPU and GPU selections can coexist. Supported devices are selected by default after capability detection. CPU fallback is always enabled; GPU selections use CUDA then DirectML priority. Detection requires workspace trust and the configured Python runtime; it does not overwrite manual selections. onnx-light and Hugging Face validation remain CPU-only. Open Settings → Engine for onnxruntime and onnx-light subtabs. CPU thread counts belong to their engine; the CPU memory arena, exported provider configuration, GPU device IDs and memory limits belong to onnxruntime. These pages share the session controls used by Prompt; changes apply to the next run and remain in this viewer panel, without changing the selected execution engine. Reference selection and validation remain on Prompt. Open Settings → Generation for temperature and maximum new tokens, shared by both prompt engines. Use Left/Right arrows, Home or End to switch categories or engine subtabs from their tab buttons.

Diagnostics and help#

View action history, progress/errors, native-library status, recovery after caught exceptions, keyboard/mouse controls and ONNX repository links. See Action logs and application status, Zoom, navigation and moving nodes and Links.

Not yet available#

The following are not implemented features of the default branch. A capability in onnx-light, onnx-light-cpu or ONNX Runtime does not imply a corresponding viewer control.

Model saving and encrypted ModelProto I/O

Other graph transformations
