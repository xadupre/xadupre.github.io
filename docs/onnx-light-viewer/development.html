Development#

Manual launch#

The simplest development loop is start.sh. To launch manually instead:

npm ci
npm run compile

Open the repository in VS Code and press F5 to launch the Extension Development Host. Run ONNX Light Viewer: Open Graph in that window’s Command Palette to open the one-node demo.

npm run compile bundles the Markdown renderer and its licenses into media/vendor/, then builds the native binding and TypeScript. TypeScript 7 uses the Node.js ambient types explicitly enabled in tsconfig.json. npm run watch watches TypeScript only; compile the native binding first, and rebuild it with npm run build:native after editing C++.

The first native build downloads the published onnx-light C++ archive pinned in CMakeLists.txt and verifies its SHA-256 checksum. Only the Node-API binding is compiled; onnx-light is not rebuilt. The archive is reused from build/native/. The binding must match the extension host’s OS and architecture, including Linux for Remote WSL.

Tests and formatting#

Run from the repository root:

npm test
npm run format:check
clang-format --dry-run --Werror native/*.cc native/*.h

The Tests GitHub Actions workflow builds the binding, runs the tests and checks JavaScript/C++ formatting on pull requests and pushes to main. Its documentation job also builds Sphinx with warnings treated as errors. Results appear in the PR’s Checks tab and the repository’s Actions tab.

Nightly coverage#

The Nightly coverage workflow runs daily at 03:00 UTC on the default branch and can also be started manually from the Actions tab. Configure the repository’s CODECOV_TOKEN Actions secret to authorize uploads to Codecov.

It runs the Node tests with source-mapped TypeScript coverage and an instrumented C++ binding, then uploads separate typescript, cpp and python reports. C++ coverage includes the binding sources in native/, not the prebuilt onnx-light libraries. Python coverage executes both model generators and the Sphinx build. Coverage tools and the matching onnx-light Python wheel are installed only in this workflow; normal extension builds and tests do not require them.

Releases#

Push a new tag to build binaries and create a GitHub release automatically, with generated release notes. The Release workflow runs for all tag names and also when a release is published through GitHub.

The workflow builds and tests the native binding on Linux, macOS and Windows (x64 and ARM64), then attaches a platform-specific .vsix extension package for each target. Each package includes the compiled extension, native binding and third-party licenses. All builds must succeed before assets are published. Rerunning the workflow replaces existing assets with the same filenames.

Download the package matching the extension host’s OS and architecture (Linux for Remote WSL), then use Extensions: Install from VSIX… in VS Code. GitHub also includes the tagged source code as ZIP and tar.gz archives. The workflow does not publish to the VS Code Marketplace.

Test models#

test/models/relu.onnx contains one Relu operator with float32 input/output tensors of shape [1, 3] (IR 9, opset 13). It can also be opened in the viewer. The same model is bundled as media/relu.onnx for the command’s demo. Other small models cover custom operators, dense/sparse initializers, optional ports, an empty operator list and intentionally invalid metadata. Shape tests also cover symbolic dimensions, scalar and unknown ranks, and inference through Add, Reshape, Transpose and Cast with a raw-data constant.

To regenerate them with the Python onnx-light package available:

python3 test/models/generate_models.py

The bundled transformer example is generated separately with python3 examples/generate_tiny_llm.py. Its ONNX file is exercised directly by the native and extension tests. Initializer metadata tests also use external-file references whose payload files are intentionally absent, and more than eight connected initializers.

Python is not required to run the extension tests.

Building this documentation#

With Python 3.11 or later, run from the repository root:

python3 -m pip install -r docs/requirements.txt
python3 -m sphinx -n -W --keep-going -b html docs build/docs/html

Open build/docs/html/index.html in a browser. Generated HTML is ignored by Git. Documentation dependencies are separate from the extension’s dependencies.

The documentation uses PyData Sphinx Theme, like onnx-light, with a light/dark theme switcher in the navigation bar. By default, it follows the system theme.

Source layout#

See Application design for the component responsibilities, native ownership rules, graph contracts and webview message protocol.

  • src/extension.ts: VS Code integration and model opening.

  • src/graph.ts: graph types and the typed native entry point.

  • native/: native entry points, model ownership, I/O, snapshots and algorithms.

  • media/viewer.js and media/viewer.css: graph rendering and layout.

  • media/logo.svg: extension logo.
